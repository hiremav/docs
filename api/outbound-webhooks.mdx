Mav's outbound API lets you subscribe to live activity from your playbooks. Every time a subscribed event or outcome fires on a lead, Mav sends a JSON POST to your configured webhook URL. You can subscribe to a single activity, a subset, or every activity your playbook supports — subscriptions are fully à la carte and configured per playbook.

This is how you keep your CRM, data warehouse, or downstream automations in sync with what Mav is doing without ever polling for updates.

<Note>
  On **Mav.next**, you set up webhooks per agent as [lead boxes](/mav-next/lead-boxes), not on a playbook. The [notification events reference](/mav-next/notification-events) lists the events. Delivery works the same way. The payload carries a `contact` object where Classic carries a `lead` object.
</Note>

---

## Configuring Webhook Subscriptions

Webhook URLs are configured inside each playbook's settings:

1. Open the Mav dashboard and navigate to your **Playbook**.
2. Go to **Settings → Activity Subscriptions**.
3. Add your HTTPS endpoint URL.
4. Select the specific events and/or outcomes you want to receive.
5. Save your changes — subscriptions take effect immediately for new activity.

You can register multiple URLs if you need to fan out activity to more than one downstream system. Each URL can subscribe to a different set of activities.

<Note>
  Subscriptions are per-playbook. If you run multiple playbooks, configure webhook URLs in each one separately.
</Note>

## Payload Structure

Mav sends one `POST` for each activity. The body is a JSON object with two nested objects:

- `activity` describes what happened.
- `lead` (Classic) or `contact` (Mav.next) describes the person it happened to.

The fields are nested, not flat. Read the label from `activity.label`, not `activity_label`.

### Activity Fields

<ResponseField name="activity.type" type="string" required>
  The kind of activity. One of `event`, `outcome`, or `conversion`.
</ResponseField>

<ResponseField name="activity.label" type="string" required>
  The name of the activity that fired, such as `qualified`, `opted_out`, or `started`. See [Events](/api/events) and [Outcomes](/api/outcomes) for the full lists.
</ResponseField>

<ResponseField name="activity.play_id" type="string | null">
  The Classic play this activity belongs to. A play is one lead's run through a playbook. This field is `null` on Mav.next.
</ResponseField>

<ResponseField name="activity.next_engagement_id" type="string | null">
  The Mav.next engagement this activity belongs to. This field is `null` on Classic.
</ResponseField>

<ResponseField name="activity.note" type="string">
  A short summary of what happened.
</ResponseField>

<ResponseField name="activity.properties" type="object">
  Extra details that some activities carry. Often empty.
</ResponseField>

<ResponseField name="activity.created_at" type="string (ISO 8601)">
  When the activity happened, in UTC.
</ResponseField>

<ResponseField name="activity.updated_at" type="string (ISO 8601)">
  When Mav last changed the activity, in UTC.
</ResponseField>

### Lead Fields (Classic)

<ResponseField name="lead.id" type="string" required>
  Mav's ID for the lead.
</ResponseField>

<ResponseField name="lead.first_name" type="string">
  The lead's first name.
</ResponseField>

<ResponseField name="lead.last_name" type="string">
  The lead's last name.
</ResponseField>

<ResponseField name="lead.email" type="string">
  The lead's email address.
</ResponseField>

<ResponseField name="lead.phone" type="string">
  The lead's phone number.
</ResponseField>

<ResponseField name="lead.status" type="string">
  The lead's status in Mav, such as `Stopped` or `Outcome - Qualified`.
</ResponseField>

<ResponseField name="lead.opted_out" type="boolean">
  `true` if the lead opted out of messages, for example by texting STOP. Check this field before you reach out through your own systems.
</ResponseField>

<ResponseField name="lead.created_at" type="string (ISO 8601)">
  When Mav created the lead, in UTC.
</ResponseField>

<ResponseField name="lead.additional_info" type="object">
  The lead's custom fields. Any field you send on intake that Mav doesn't map lands here under the same name.
</ResponseField>

<ResponseField name="lead.originators" type="array">
  The systems the lead came from. Every lead has a `mav` originator. A lead you create through the Leads API with an originator also carries that one.

  <Expandable title="lead.originators item">
    <ResponseField name="origin" type="string">
      The originating system, such as `mav`, `hubspot`, or `custom`.
    </ResponseField>
    <ResponseField name="key" type="string">
      The lead's ID in that system.
    </ResponseField>
    <ResponseField name="created_at" type="string (ISO 8601)">
      When Mav recorded the originator, in UTC.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="lead.plays" type="array">
  Every play run on the lead. Each play lists its own activities.
</ResponseField>

<ResponseField name="lead.playbook" type="object">
  The playbook behind the lead's current play.
</ResponseField>

<ResponseField name="lead.referral" type="object">
  Referral details, when the lead has them.
</ResponseField>

<ResponseField name="contact.id" type="string" required>

## Matching Leads Back to Your CRM

Send your own ID for the lead as an extra field when you submit it through a Marketing Source. Mav doesn't map unknown fields, so your ID lands in `additional_info` under the same name. Every webhook for that lead carries it back.

For example, if you submit `"your_crm_id": "crm-lead-id-456"`, read it from `lead.additional_info.your_crm_id` on Classic or `contact.additional_info.your_crm_id` on Mav.next. You can then look up the record in your system without matching on name or email.

## Delivery

### Authentication

Mav supports two auth options per webhook:

- **None.** Mav sends no auth header.
- **Bearer.** Mav sends your token in an `Authorization: Bearer <token>` header.

Mav doesn't support other auth headers, such as `X-Api-Key`. If your endpoint needs a key, read it from the `Authorization` header.

### Responses and Retries

- Mav waits 3 seconds for your endpoint to connect and 3 seconds for it to reply.
- Any `2xx` reply counts as delivered.
- Mav doesn't follow redirects. A `3xx` reply counts as a failure.
- Mav retries a failed delivery up to 18 times over about four days.
- If the last retry fails, Mav turns off the webhook and emails your account's admins and managers.

Reply with `200` as soon as you receive the payload. Then process it on your side.

## Best Practices

### Use HTTPS

Serve your webhook endpoint over HTTPS with a valid TLS certificate from a trusted CA. Payloads carry personal data.

### Design for Idempotency

A retry can deliver the same payload twice. Make your handler safe to run twice on the same payload. Payloads carry no activity ID, so build a key from the person's ID, `activity.label`, and `activity.created_at`.

### Validate the Payload Shape

Check that `activity.type`, `activity.label`, and `lead.id` or `contact.id` exist before you process a payload. Handle activity labels you don't recognize without failing. Mav adds new ones over time.

### Log Raw Payloads

Store the raw incoming payload before processing it. This gives you a reliable audit trail and makes debugging much easier if something goes wrong downstream.
